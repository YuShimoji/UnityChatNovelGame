# Feature Registry

> done は「初期仕様の実装完了」を意味し、「改善の余地がない」を意味しない。
> このレジストリは、実装済み機能への改善候補・拡張フェーズ・UIバグを構造的に受け容れる。

## 運用ルール

### spec-index の done と Enhancement の関係

spec-index の status は**初期仕様のライフサイクル**を追跡する:
- `done`: 初期仕様として定義された機能の実装が完了
- `partial`: 初期仕様の一部が未実装
- `todo`: 初期仕様が未着手

done 済み仕様に対する追加要望は、ここに **Enhancement (ENH)** として登録する。
spec-index の status を done から戻す必要はない。

### Enhancement の状態

| 状態 | 意味 |
| ---- | ---- |
| candidate | 改善候補として認識。仕様未定義 |
| specified | 仕様が定義済み。実装承認待ち |
| approved | 実装承認済み。着手可能 |
| in-progress | 実装中 |
| done | 完了 |
| hold | 保留 (前提条件未充足、優先度低) |
| rejected | 不採用 |

### Enhancement の登録基準

以下に該当するものを登録する:
- done 済み仕様に対する機能追加・拡張フェーズ
- 仕様に含まれない UI/UX の改善
- 実使用で発見された摩擦や不足
- Yarn オーサリング側から見た制御の拡張

以下は登録しない:
- バグ修正 (UI_ISSUES.md へ)
- テスト追加 (EN-012 のスコープ)
- ドキュメント更新のみ

## 改善候補の傾向パターン

done 済み仕様から改善候補が生まれる典型的なパターン:

### 1. 制御の粒度拡張
初期実装は on/off だが、実使用でグラデーションが必要になる。
- 例: タイプライター速度 (固定→可変)、ヒント表示 (全体→チャンネル別)

### 2. Yarn オーサリングからの制御追加
エンジン側は動作するが、ライターが Yarn から細かく演出を制御する手段がない。
- 例: タイプライター中間停止、バブルスタイル変更、条件付き演出

### 3. 状態遷移のアニメーション化
機能は動作するが、状態変化が瞬間的で没入感が薄い。
- 例: スレッド切替、HalluciCoin 獲得、チャプター遷移

### 4. フィードバックの深化
操作結果が分かりにくい、または物足りない。
- 例: 選択肢の結果、矛盾発見の演出、進捗の可視化

### 受け容れフロー

```
実使用で気づく → candidate 登録 → 仕様定義 (specified) → 承認 (approved) → 実装
                      |
                      +→ hold (今ではない)
                      +→ rejected (不要と判断)
```

- candidate の登録は随時。セッション中に気づいたらここに追記する
- specified への昇格は PLAN MODE で仕様を定義してから
- approved への昇格はユーザー承認が必要
- 実装は approved のもののみ。candidate を直接実装しない
