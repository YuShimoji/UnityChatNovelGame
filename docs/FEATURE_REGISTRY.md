# Feature Registry

> done は「初期仕様の実装完了」を意味し、「改善の余地がない」を意味しない。
> このレジストリは、実装済み機能への改善候補・拡張フェーズ・UIバグを構造的に受け容れる。

## 運用ルール

### spec-index の done と Enhancement の関係

spec-index の status は**初期仕様のライフサイクル**を追跡する:
- `done`: 初期仕様として定義された機能の実装が完了
- `partial`: 初期仕様の一部が未実装
- `todo`: 初期仕様が未着手

done 済み仕様に対する追加要望は、ここに **Enhancement (ENH)** として登録する。
spec-index の status を done から戻す必要はない。

### Enhancement の状態

| 状態 | 意味 |
| ---- | ---- |
| proposed | 改善候補。調査・比較・破棄可能な低コスト試作は可。本番統合は未承認 |
| approved | 実装承認済み。着手可能 |
| in-progress | 実装中 |
| done | 完了 |
| hold | 保留 (前提条件未充足、優先度低) |
| rejected | 不採用 |
| quarantined | 出所・承認範囲が不確実。個別再確認まで通常候補として扱わない |

### Enhancement の登録基準

以下に該当するものを登録する:
- done 済み仕様に対する機能追加・拡張フェーズ
- 仕様に含まれない UI/UX の改善
- 実使用で発見された摩擦や不足
- Yarn オーサリング側から見た制御の拡張

以下は登録しない:
- バグ修正 (UI_ISSUES.md へ)
- テスト追加 (EN-012 のスコープ)
- ドキュメント更新のみ

提案を登録するときは、タイトルだけでなく次を短く添える。

- 仮説と、利用者または制作工程への効果
- 解く bottleneck と統合先
- 同じ条件で比較できる最小試作または証拠
- actor / owner artifact
- 承認後に凍結する受入条件

`proposed` の調査・比較は明示承認なしで行える。製品コード・本編コンテンツ・長寿命アセットへ統合する前に `approved` が必要になる。
未承認の比較は scratch、DQT、または一時複製を使い、checked-in の本番設定を直接上書きしない。不採用の一時 asset / scene 状態は同じ CLOSE で除去し、比較証拠と判断理由だけを必要に応じて残す。

## 改善候補の傾向パターン

done 済み仕様から改善候補が生まれる典型的なパターン:

### 1. 制御の粒度拡張
初期実装は on/off だが、実使用でグラデーションが必要になる。
- 例: タイプライター速度 (固定→可変)、ヒント表示 (全体→チャンネル別)

### 2. Yarn オーサリングからの制御追加
エンジン側は動作するが、ライターが Yarn から細かく演出を制御する手段がない。
- 例: タイプライター中間停止、バブルスタイル変更、条件付き演出

### 3. 状態遷移のアニメーション化
機能は動作するが、状態変化が瞬間的で没入感が薄い。
- 例: スレッド切替、HalluciCoin 獲得、チャプター遷移

### 4. フィードバックの深化
操作結果が分かりにくい、または物足りない。
- 例: 選択肢の結果、矛盾発見の演出、進捗の可視化

### 受け容れフロー

```
実使用で気づく → proposed 登録 → 調査・同条件比較 → 承認 (approved) → 実装
                     |
                     +→ hold (今ではない)
                     +→ rejected (不要と判断)
```

- proposed の登録、調査、破棄可能な比較試作は随時行える
- approved への昇格は、受入条件を定義しユーザーが製品実装を承認したときだけ
- 製品コード・本編・長寿命アセットへの統合は approved のものだけ。比較試作をそのまま製品実装へ昇格させない
