# Interaction Notes

報告UI・手動確認・質問形式に関する project-local メモ。

## 手動確認の発動条件 (最優先)

- フル通しや回帰目的の手動確認は **SUBSEQUENT スライス発動時のみ**。通常の実装スライス / 微修正では要求しない。`HANDOFF` / Work Packet に明示された可視受入スライスは、対象面をまとめて 1 回だけ確認できる
- DIRECTION CHECK はテストや手動検証ではなく、高手戻りの主観方向を実装前に選ぶ意思決定である
- **視覚・挙動変更を伴わない修正** (文書修正 / Yarn 内部ノード追加 / リファクタ / 内部文字列調整) で手動確認を要求することは **禁止**
- 手動確認・テスト実行は「進展の証明」ではない。スライス進捗に対して確認コストが過大な場合、確認範囲を縮小する側で判断する
- 1 ブロック内で複数の微修正が発生した場合、**バッチの終端で 1 回だけ**手動確認を提案する (毎修正ごとではない)

## 手動確認の出し方

- 手動確認項目は本文で提示する
- AskUserQuestion では OK / NG番号 だけを聞く
- 手動確認依頼と次アクション選択を同じ質問に混ぜない

## 禁止パターン

- AskUserQuestion の question に Markdown テーブルを入れる
- 選択肢を commit / しない の yes/no で埋める
- 既知文脈を「詳細を教えてください」で再質問する
- 「フォントサイズを変えたので確認してください」のような微修正確認ループ
- 1件の UI 問題ごとに手動確認を求める (一括処理すること)
- エンジン能力の前進を伴わないコンテンツ作業を 2 セッション以上連続で主成果とすること
- 実装、関連修正、検証、現在地更新を別々の Prompt に分解すること
- 軽微なリスクや通常の警告を報告し、そのたびに続行許可を待つこと
- 主観的で手戻りの大きい見た目を完成品まで作ってから、初めてユーザーの方向性を確認すること

## ユーザーが嫌う形式

- 進路選択を狭める二択
- 作業量に見合わない微修正の繰り返し提案
- 全ての作業が先送りになる保守偏重の選択肢
- 「前回の反動」で振り子的に方向を決める提案 (UI修正が続いた→次はコンテンツ、ではなく本当に必要なものを特定する)
- AI がユーザーの仕事 (執筆) を代行しようとする提案。AI はシステム/ツールを整備する側
- done 済み仕様を「完了」として閉じ、改善候補が入る余地がないロードマップ。個々の機能ではなく傾向と受け入れ構造が重要
- テスト失敗に対して「テストパスのために実装を変える」対応。まずテスト自体の前提を疑う

## 創造提案と方向確認

- レイアウト、言語対応、隣接コンテンツ、色、フォント、アニメーションは、active slice と接続できる場合に AI から自発提案してよい。
- 高手戻りな主観判断は、同一条件の 2–3 案、推奨、最小見本を実装前に提示し、方向確認を 1 回だけ行う。確認には、選択が承認する本番統合範囲を明記する。
- 選択は 1 案 approve / 全案 hold / reject、選択案への必須修正は 1 点まで。受入条件を凍結して実装・関連修正・局所検証をバッチ完遂し、比較案そのものを反復研磨しない。追加要望は `FEATURE_REGISTRY.md` または `UI_ISSUES.md` へ分離する。
- 選択肢は保守案だけで同質化させない。前進、監査、削除、探索など異なる bottleneck を解く入口を用意し、「完了すると何が可能になるか」を示す。

## 報告メモ

- セッション成果を報告する際、「エンジン/ツール能力として何が前進したか」を最初に示す。コンテンツ前進は二番目。コンテンツのみのセッションだった場合、次セッション冒頭でドリフト警告を発する
- UI 値調整は Inspector 作業として扱い、セッション成果に含めない
- handoff は固定英語ラベルを並べず、`docs/HANDOFF.md` の現在地を置換する。履歴 snapshot を追記しない
- handoff 前に `git status`、関連検証、正本反映を確認する
- 変更・選択肢・残作業が複数ある完了報告では、本文を補助する比較表を使う。固定英語ラベルを薄く並べる形式ではなく、実際の摩擦・効果・次の動きが伝わる自然な日本語にする
- 完了報告の末尾には、次に入れる取っ掛かりを 2〜4 個出す。各入口はどの bottleneck を減らし、選ぶと次に何が可能になるかまで短く添える

## 運用ルール

- ユーザーの報告形式の好みや嫌いなパターンが判明したらここに追加する
