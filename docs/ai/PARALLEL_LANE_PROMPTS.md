# 監修 AI → 開発 AI Work Packet

このファイルは、監修側が開発側へ渡す Prompt を細切れにしないためのコピペ用テンプレートである。旧レーン別プロンプト集のように Content / UI / Audit を別 Prompt へ分けない。1 Packet は、1 つの成果状態を実装・関連修正・局所検証・現在地更新まで閉じられる単位にする。

## 監修側の作成ルール

- 正本にある背景を再掲せず、参照先と今回の差分だけを書く。
- ファイル名や細かな手順ではなく、成果、境界、受入条件を固定する。
- 開発側に実装方法の裁量を残す。
- 先に決める必要がある主観的方向は最大 1 件にまとめる。なければ「なし」とする。
- 軽微な報告で停止させず、関連修正、狭い検証、`HANDOFF` 更新までを明示的に含める。
- UI、テスト、docs を別 Packet に切り出すのは、それ自体が独立した成果状態を持つ場合だけにする。

## 貼り付け用テンプレート

```text
【成果状態】
完了時に、誰が何をできるようになっているかを1〜3文で記述する。

【今やる理由】
現在の bottleneck と、それを示す確認済み根拠を記述する。

【正本】
docs/REPO_LOCAL_RULES.md と docs/HANDOFF.md。
今回の実作業に直接必要な追加正本だけを列挙する。docs/archive/ は読まない。

【固定済み】
変更してはいけない仕様、ユーザー所有の判断、既に承認された方向を記述する。

【開発側の裁量】
実装方法、必要な関連修正、狭いテスト、内部構造など、開発側が自律判断してよい範囲を記述する。

【範囲外】
今回広げない領域を記述する。偶発的なUI問題は UI_ISSUES.md、未承認案は FEATURE_REGISTRY.md へ送る。

【先に決める方向】
なし。
または、高手戻りの主観判断を1件だけ記述する。開発側は同一条件の2〜3案、推奨、最小見本を提示し、選定を1回待つ。質問には「選択すると承認される本番統合範囲と受入条件」を明記する。選択は1案approve / 全案hold / reject、必須修正は1点まで。選定後は細部ごとに停止せず、不採用の一時試作はCLOSEで除去する。

【完了判定】
- 利用者または制作工程で観測できる受入条件
- 実行する最小の自動・静的検証
- 自動化できない場合だけ、バッチ終端の目視項目

【自走範囲】
実装 → 必要な関連修正 → 局所検証 → git diff/status確認 → HANDOFFのライブ現在地更新まで継続する。
軽微な警告、通常の実装判断、可逆な仮定では停止しない。仮定は完了報告に残す。

【停止条件】
docs/REPO_LOCAL_RULES.md の Execution Default に従う。
破壊的変更、依存追加、DB/save/auth/API契約変更、仕様衝突、外部副作用の権限不足だけをまとめて確認する。

【完了報告】
成果を先に自然文で説明し、検証、残る不確実性、異なる bottleneck を解く2〜4個の次入口を示す。固定英語ラベルの穴埋めはしない。
```

## Work Packet の大きさ

適切な Packet は、次のどちらかである。

- **直接実装 Packet**: 方向が決まっており、可逆な実装から CLOSE まで一気に進められる。
- **方向確認つき Packet**: 最小比較を作るところまで進み、方向選定を 1 回だけ挟んだ後、選択案を CLOSE まで完遂する。

不適切な分割例:

- 調査だけ、実装だけ、テストだけ、docs 更新だけを順番に別 Prompt で渡す。
- 1 ファイル修正ごとに次 Prompt を要求する。
- 「安全のため」という理由だけで、既知の受入条件を再確認する。

## 並行化

並行エージェントは、競合しない調査、検証、比較案作成へ使う。主実装と `HANDOFF` 更新の owner は 1 つにする。同じ大きな `.cs`、scene、asset を複数 Packet で同時編集しない。
